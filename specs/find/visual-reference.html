3. The two count semantics

FND-13, FND-14, FND-15

The single easiest requirement to lose in implementation. An entity type count reports what currently matches. A search field count reports what that field alone would match, whether or not it is scoped in. That is why a zero beside a ticked field is information, and why the field holding the answer announces itself before the user has ticked it.

Entity types, count = what matches now

Every type is scoped in and every count is zero. Nothing matches. Widening the type scope will not help, which is why that remedy renders disabled.

Search fields, count = what it alone would match

Two fields are scoped in and both are zero. Definition is not scoped in and reports 1. The answer is one tick away and the rail says so without being asked.

5. The statement table

FND-47, FND-48, FND-49, FND-50, FND-52, FND-53

A predicate carrying a disclosure affordance is changeable. A predicate without one is fixed. That affordance is the only signal distinguishing the two, so it is never applied decoratively. An individual's parent is a second rdf:type row, not rdfs:subClassOf, because presenting it as a subclass axiom is an error in the ontology and not only in the interface.

10. Where these composites belong

FND-81, FND-82, FND-83

Nothing on this page is a Find component. The section panel, the ancestry chain, the statement table, the add row action and the Source disclosure came from the Details view and will be wanted by the Add entity view and the class inspector. Specifying them inside a surface document is provisional, and leaving them there is how a product ends up with views that look different.
